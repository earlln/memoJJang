# 인코딩 처리 규칙

메모짱이 파일을 읽고 쓸 때 인코딩을 어떻게 판단하고 다루는지 정리한 문서입니다.
구현은 `Services/EncodingDetector.cs` 와 `Services/TextFileService.cs` 에 있습니다.

## 1. 읽기 — 감지 순서

파일 전체를 바이트로 읽은 뒤 아래 순서로 판단합니다. (표본 최대 64 KB)

### 1단계 · BOM

| 선두 바이트 | 판정 | BOM 길이 |
| --- | --- | --- |
| `FF FE 00 00` | UTF-32 LE | 4 |
| `00 00 FE FF` | UTF-32 BE | 4 |
| `EF BB BF` | UTF-8 (BOM 포함) | 3 |
| `FF FE` | UTF-16 LE | 2 |
| `FE FF` | UTF-16 BE | 2 |

> `FF FE 00 00` 을 `FF FE`(UTF-16 LE)보다 **먼저** 검사합니다.
> 순서를 바꾸면 UTF-32 LE 파일이 UTF-16 LE 로 잘못 읽힙니다.

### 2단계 · BOM 없는 UTF-16 추정

널 바이트(`0x00`)가 **한쪽 위치에만** 몰려 있는지 봅니다.

- 홀수 위치에만 몰림 → UTF-16 **LE**
- 짝수 위치에만 몰림 → UTF-16 **BE**

전체 문자 수의 30% 이상이고 반대쪽 위치에 널이 하나도 없을 때만 인정합니다.
(일반 텍스트나 이진 파일을 UTF-16 으로 오판하지 않기 위한 보수적인 기준입니다.)

### 3단계 · UTF-8 유효성 검사

직접 구현한 엄격한 검사기로 다음을 모두 거릅니다.

- 선두 바이트로 올 수 없는 값 (`0x80`~`0xC1`, `0xF5`~`0xFF`)
- 후속 바이트가 `10xxxxxx` 가 아닌 경우
- 과잉 인코딩(overlong): 3바이트로 `U+0800` 미만, 4바이트로 `U+10000` 미만
- 서로게이트 영역 `U+D800`~`U+DFFF`
- `U+10FFFF` 초과

결과에 따라

| 검사 결과 | 판정 |
| --- | --- |
| 유효 + 비 ASCII 문자 있음 | **UTF-8** (BOM 없음) |
| 유효 + 순수 ASCII | **ANSI** — 윈도우 기본 메모장과 같은 표기입니다. 바이트가 동일하므로 손실은 없습니다. |
| 유효하지 않음 | 4단계로 |

### 4단계 · 폴백

시스템 ANSI 코드 페이지를 사용합니다.
한국어 Windows 에서는 **CP949(EUC-KR)** 입니다.

> `.NET`(Core)의 `Encoding.Default` 는 항상 UTF-8 이라서 ANSI 코드 페이지가 아닙니다.
> 그래서 `CultureInfo.CurrentCulture.TextInfo.ANSICodePage` 값을 직접 읽고,
> `CodePagesEncodingProvider` 를 등록해 CP949 같은 레거시 인코딩을 사용할 수 있게 합니다.

감지 결과와 그 근거는 상태 표시줄에 `(UTF-8 BOM)`, `(순수 ASCII)` 처럼 표시됩니다.
감지가 틀렸다면 **인코딩 메뉴 → 다른 인코딩으로 다시 열기**로 원본 바이트에서 다시 디코딩할 수 있습니다.

## 2. 지원 인코딩

| 항목 | 코드 페이지 | BOM |
| --- | --- | --- |
| ANSI (시스템 기본) | 로캘에 따름 (한국어 = 949) | 없음 |
| UTF-8 | 65001 | 없음 |
| UTF-8 (BOM 포함) | 65001 | 있음 |
| UTF-16 LE | 1200 | 있음 |
| UTF-16 BE | 1201 | 있음 |
| UTF-32 LE | 12000 | 있음 |
| 한국어 EUC-KR | 949 | 없음 |
| 일본어 Shift-JIS | 932 | 없음 |
| 중국어 간체 GB18030 | 54936 | 없음 |
| 중국어 번체 Big5 | 950 | 없음 |
| 서유럽 Windows-1252 | 1252 | 없음 |
| 서유럽 ISO-8859-1 | 28591 | 없음 |

ANSI 와 코드 페이지가 겹치는 항목은 목록에 중복 노출하지 않습니다.
(한국어 Windows 에서는 `ANSI` 가 곧 CP949 이므로 `EUC-KR` 항목이 숨겨집니다.)

BOM 없는 UTF-16/UTF-32 BE 는 **자동 감지 결과로만** 쓰이고 메뉴에는 나오지 않습니다.

## 3. 줄 바꿈

편집기 안에서는 **항상 `CRLF` 로 정규화**해서 다룹니다.
이렇게 하면 줄·열 계산과 찾기·바꾸기가 파일 원본 형식과 무관하게 일관됩니다.

파일을 읽을 때 가장 많이 쓰인 줄 바꿈을 문서의 형식으로 잡고,
저장할 때 그 형식으로 되돌립니다.

| 형식 | 시퀀스 | 표시 |
| --- | --- | --- |
| Windows | `\r\n` | `CRLF` |
| Unix / Linux / macOS | `\n` | `LF` |
| 고전 Mac | `\r` | `CR` |

상태 표시줄의 `CRLF` 를 눌러 언제든 바꿀 수 있습니다.

## 4. 쓰기

1. `CRLF` 로 정규화된 본문을 문서의 줄 바꿈 형식으로 변환합니다.
2. **손실 검사** — `EncoderFallback.ExceptionFallback` 을 붙인 인코딩으로 시험 인코딩해 봅니다.
   표현할 수 없는 문자가 있으면 그 문자와 위치를 알려 주고
   `UTF-8 로 저장 / 그대로 저장 / 취소` 를 묻습니다.
3. **원자적 저장** — 같은 폴더의 임시 파일에 BOM(필요 시) + 본문을 쓰고 `Flush(true)` 한 뒤,
   `File.Replace` 로 원본과 교체합니다. 도중에 오류가 나면 임시 파일만 지우고 원본은 그대로 둡니다.

## 5. 주의점 정리

- **UTF-8 과 UTF-8(BOM 포함)은 다른 것**입니다. 웹/리눅스 도구와 주고받을 파일은 BOM 없는 UTF-8 이 안전합니다.
- **순수 ASCII 파일은 ANSI 로 표시**되지만 바이트는 UTF-8 과 동일합니다.
  여기에 한글을 넣고 저장하면 CP949 로 기록되므로, 다른 환경과 공유할 파일이라면 UTF-8 로 바꿔서 저장하세요.
- **UTF-16 LE/BE 는 항상 BOM 을 기록**합니다. BOM 없는 UTF-16 은 읽기만 지원합니다.
